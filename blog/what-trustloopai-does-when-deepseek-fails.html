What does TrustLoopAI do when DeepSeek fails in a live SMS loop?

It fails over to Gemini Flash and keeps the conversation on a transport that actually works on Node 20 — including Fly and the websocket path Supabase needs.

Shane Foster  ·  Founder, Haven Command LLC  ·  June 29, 2026

What problem did we actually hit?

Problem

TrustLoopAI is a customer-engagement loop over SMS. If the primary model — DeepSeek, in this setup — errors or times out, the customer is still sitting on a text thread. “Try again later” is not a conversation.

Separately, the app has to talk to Supabase from Node 20 on Fly. The easy HTTP assumption is not always the path that stays open. A “connected” product that cannot reach its own database is a demo with a phone number.

How did Haven Command solve it?

Solution

When DeepSeek fails, the loop falls over to Gemini Flash and continues. The customer does not need to know the roster. They need the next useful message. We log the failover so I can see cost and quality; we do not surface an autopsy in the text thread.

On the data hop, we use a websocket transport that works for Supabase on that Node 20 / Fly combination instead of pretending every runtime speaks the same dialect. This is plumbing. Plumbing is the product.

Same instinct as grounding D4Chess: do not let an upstream hole become fluent nonsense or a dead line.

A fallback model is not a luxury. It is how an SMS loop survives someone else’s outage.

Questions this write-up answers

What happens if the primary model is down?

What did Node 20 have to do with it?

The default transport assumptions did not match how Supabase needed to talk from that runtime on Fly. We used a websocket path that actually stays up.
